The comparison

This page is an excerpt from Part A2. Two paragraphs are left out: one on programming models and one on professional use. References cited only in those paragraphs are left out with them.

Both languages can solve the same problem effectively. The A1 exercise set Python and JavaScript the same task, collecting names, removing duplicates, and returning them in alphabetical order. Both scripts appeared to work on first run and contained the same logic error: names written in different capitalisation were treated as separate entries, and the output was wrong silently. The revisions corrected it through input validation and case insensitive deduplication, confirming that the underlying logic was identical even though the syntax differed. This makes it possible to move beyond the output of the scripts and compare the two languages in terms of programming model, readability and developer accessibility, error handling and debugging, and suitability for modern computing tasks. This report argues that Python provides the more accessible development model for new programmers and many analytical computing tasks, while JavaScript reflects a different set of priorities shaped by the demands of the web.

A programming language can be capable in principle, but readability affects how accessible it feels when someone is trying to learn it. Python used fewer punctuation heavy structures and focused more on word based structures, so the script was easier to follow on first reading. A line like for name in names reads almost like an English sentence, and that matters when a learner is trying to work out the logic of the code at the same time as its syntax. The JavaScript version solved the same problem, but it expressed that logic through braces, semicolons, and the spread operator, which made the script more compact but also more demanding for someone unfamiliar with those conventions. That point fits with Lutz's (2013) view that writing high quality code has to remain readable even as projects become more complex. Havill (2021) argues that accessibility in introductory programming depends on more than just syntax. By organising his textbook around interdisciplinary problems, algorithm design, and computational thinking rather than around isolated language features, he treats Python primarily as a tool for problem solving and discovery. Walton (2024) suggests that programming language readability is shaped in part by the linguistic and cultural conventions embedded in syntax, which helps explain why Python is often experienced as clear and accessible by beginners. The A1 evidence only partially supports that framing, however. Both scripts encoded identical logic, which suggests the readability difference is less about cultural convention and more about the explicitness of Python's syntactic choices: words over punctuation, names over symbols. This does not imply that languages such as JavaScript are unreadable; experienced users can navigate their conventions with ease. Even so, taken together, both the literature and the Part A1 exercise suggest that Python is the more approachable place to begin.

The A1 exercise exposed something that matters more than syntax: neither script crashed, yet both produced the wrong result. That distinction between a runtime failure and a silent logic error is central to how each language handles mistakes in practice. Lutz (2013) presents Python's exception handling model as part of the language's core design, which means defensive checks can be built into a script without changing its basic structure. The revised Python script from A1 did exactly that, rejecting invalid input before any processing began. Python’s isinstance check makes the assumption explicit. Rather than letting the code guess what it has been given, it states the requirement directly in the function. JavaScript’s Array.isArray does the same thing, but the reason it exists is different. JavaScript was built for the browser, where a function might be called by a form, an API response, or a user clicking a button. It cannot assume what is coming in, so the check has to be written in. When Python raises a TypeError, it produces a traceback naming the exact file, line number, and error type. A JavaScript try/catch block achieves the same structural result, but a browser console error requires the developer to also interpret the runtime environment, distinguishing between the code itself, the engine executing it, and the platform in which it runs. The comparison is not that JavaScript handles errors poorly, but that Python tends to make the debugging process more transparent for someone still learning how errors behave.

What matters more is who is writing the code, what the task demands, and where the code has to run. Python reduces entry barriers and supports readable scripting, but that is not the same as being a better language. JavaScript’s complexity is not a flaw. It reflects what the web asks of it. The right tool is the one the task requires.
