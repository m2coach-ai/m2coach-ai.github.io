Portfolio reflection

From explanation to evidence

The module showed me that explaining a technical idea and demonstrating it are not the same thing.

  2. What
  3. So what

About this reflection

About this page: Written for this e-portfolio after the module. It was not part of a submitted assessment. It follows the What, So What, Now What structure, and each claim links to the artefact passage that supports it.

What

I entered Module 1 with considerable experience explaining processes to other people. That gave me confidence in communication, but the module showed me that explaining a technical idea and demonstrating it are not the same thing. In A1: Code Exploration, I initially described what two scripts were designed to do: collect names into a set, remove duplicates and return them in alphabetical order. Testing showed that they did not do it. Duplicates persisted in the output, because capitalisation variants were treated as separate people, and the code ran without crashing. The silent failure in A1 shows both what I understood and what I had not yet made visible.

My response was to test both scripts across four input categories, then replace the set with a dictionary keyed on the lowercase name, and add a check that stops the function at once if it is not given a list. That revision matters because it records a decision rather than hiding the earlier weakness behind a polished final product. The modification and its output show the change and its result.

Where to see it

  • Duplicates persisted and the code ran without crashing: Part A1: the silent failure
  • Both scripts tested across four input categories: Part A1: test results
  • The set replaced by a dictionary, with a check on the input type: Part A1: the modification and the scripts

So what

The experience challenged one of my assumptions. I had treated clear explanation as evidence that I understood the process. The artefact showed that clarity only becomes reliable when the underlying decision can also be examined, repeated or tested, as the test results across four input categories show.

As an educator, I often ask students to show their process. Module 1 made that expectation apply more directly to my own work. The marker asked for a “clearer distinction between descriptive explanation and evaluative discussion” (marker’s feedback on A1). If I claim that my understanding changed, the portfolio should let a reader see where it changed and what caused the change.

Where to see it

  • Clarity checked by testing: Part A1: test results
  • The marker’s distinction between description and evaluation: Marker’s feedback on Part A1

Now what

I will treat traceability as part of the work rather than something added afterward. For each substantial task, I will retain the important decision, the evidence used to check it and the limitation that remains. This will make later reflections more specific and make my progress easier to evaluate.

Contribution statement

The experience and interpretation are my own. I used the ACM Code of Ethics and Professional Conduct (ACM, 2018), principle 2.5, for the idea that systems whose risks cannot be reliably predicted should undergo frequent reassessment or not be deployed. I selected the evidence, judged what it proved and wrote the final claim.
